> 本文档整理了「智能能源终端」项目中涉及的嵌入式面试高频考点。
> 每道题均标注了**与项目的关联点**，方便面试时结合项目经历作答。

## 一、ARM Cortex-M4 内核

### Q1：Cortex-M4 的中断优先级是怎么管理的？

**答：** Cortex-M4 通过 NVIC（嵌套向量中断控制器）管理中断优先级。

- 优先级分为**抢占优先级**和**子优先级**，由优先级分组决定各占几位
- STM32F407 使用优先级寄存器的高 4 位（0~15），数值越小优先级越高
- 三个固定最高优先级异常：Reset（-3）、NMI（-2）、HardFault（-1）
- 相同抢占优先级的中断不能互相抢占，按子优先级决定响应顺序
- 相同抢占 + 子优先级时，按中断号（硬件编号小的优先）决定

**项目关联：** 本项目使用 `NVIC_PRIORITYGROUP_4`（4 位全部用于抢占优先级，无子优先级），后续集成 FreeRTOS 时需要注意 `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY` 的设置，高于此优先级的中断不受 FreeRTOS 管理。

---

### Q2：HardFault 是什么？怎么调试？

**答：** HardFault 是 Cortex-M 中优先级最高的可编程异常（优先级 -1），当其他 Fault（MemManage、BusFault、UsageFault）未使能或处理失败时，都会升级为 HardFault。

**常见触发原因：**
- 访问非法内存地址（空指针、越界）
- 栈溢出覆盖了关键数据
- 在不可执行区域取指令
- 未对齐的内存访问（某些情况下）

**调试方法：**
1. 在 `HardFault_Handler` 中通过汇编获取故障时的栈帧指针（MSP 或 PSP）
2. 从栈帧中读取 PC（程序计数器），定位出错的代码行
3. 读取 SCB->CFSR 寄存器，分析具体的故障类型
4. 读取 SCB->BFAR 或 SCB->MMFAR，获取触发故障的内存地址

**项目关联：** 本项目当前 `HardFault_Handler` 是 CubeMX 生成的 `while(1)` 死循环，已列入待优化项，计划替换为寄存器打印诊断或 `NVIC_SystemReset()` 自动复位。

---

### Q3：Cortex-M4 的 MSP 和 PSP 有什么区别？

**答：**
- **MSP（Main Stack Pointer）：** 主栈指针，复位后默认使用，用于特权模式和异常处理
- **PSP（Process Stack Pointer）：** 进程栈指针，用于用户线程

裸机程序只使用 MSP。引入 RTOS 后，每个任务使用独立的 PSP，中断处理仍使用 MSP，这样任务栈溢出不会破坏中断处理的栈空间。

**项目关联：** 当前裸机阶段只使用 MSP。后续集成 FreeRTOS 后，每个任务会分配独立的栈空间（PSP），需要合理配置每个任务的栈大小，避免栈溢出导致 HardFault。

## 二、STM32 时钟系统

### Q4：STM32F407 的时钟树是怎样的？HSI 和 HSE 有什么区别？

**答：** STM32F407 有四个基本时钟源：

| 时钟源 | 频率 | 精度 | 用途 |
|--------|------|------|------|
| HSI | 16MHz 内部 RC | 较低（±1%） | 快速启动、备用时钟 |
| HSE | 4~26MHz 外部晶振 | 高（±20ppm） | PLL 输入源、高精度场景 |
| LSI | ~32kHz 内部 RC | 低 | 独立看门狗（IWDG） |
| LSE | 32.768kHz 外部晶振 | 高 | RTC 实时时钟 |

**时钟配置链路：** HSE(8MHz) → PLL 倍频 → SYSCLK(168MHz) → AHB/APB1/APB2 分频

**项目关联：** 本项目使用 HSE 8MHz 外部晶振作为 PLL 输入源，配置 PLLM=8、PLLN=336、PLLP=2，最终 SYSCLK = 8/8×336/2 = 168MHz。APB1 = 42MHz（4 分频），APB2 = 84MHz（2 分频）。

---

### Q5：为什么操作 GPIO 之前必须使能对应的时钟？

**答：** STM32 为了降低功耗，所有外设时钟**默认关闭**。外设寄存器的读写依赖总线时钟，如果时钟未使能：

- 写入外设寄存器的值**不会生效**（寄存器不响应总线操作）
- 读取外设寄存器会返回**不确定的值**

因此必须先调用 `__HAL_RCC_GPIOx_CLK_ENABLE()` 使能时钟，才能正常配置和使用 GPIO。

---

## 三、GPIO

### Q6：GPIO 的推挽输出和开漏输出有什么区别？

**答：**

| 特性 | 推挽输出（Push-Pull） | 开漏输出（Open-Drain） |
|------|----------------------|----------------------|
| 输出结构 | P-MOS + N-MOS 互补 | 仅 N-MOS |
| 能输出高电平 | 能（P-MOS 导通到 VDD） | 不能（需外部上拉电阻） |
| 能输出低电平 | 能（N-MOS 导通到 GND） | 能（N-MOS 导通到 GND） |
| 驱动能力 | 强（高低电平都有驱动） | 弱（高电平靠上拉） |
| 典型应用 | LED、SPI、USART | I2C（线与逻辑）、电平转换 |

**项目关联：** 本项目 LED 控制（PF9）使用推挽输出 `GPIO_MODE_OUTPUT_PP`；USART1 的 TX/RX（PA9/PA10）使用复用推挽 `GPIO_MODE_AF_PP`。后续 I2C 传感器接口将使用复用开漏 `GPIO_MODE_AF_OD`。

---

### Q7：GPIO 的复用功能（AF）是什么？和普通 IO 有什么区别？

**答：**
- **普通 IO：** CPU 直接通过 ODR/IDR 寄存器控制引脚高低电平（如控制 LED、读取按键）
- **复用功能（AF）：** 引脚的控制权交给**片上外设**（如 USART、SPI、I2C），由外设硬件自动驱动引脚电平

STM32F407 每个引脚最多有 16 个复用功能（AF0~AF15），通过 GPIOx_AFRL/AFRH 寄存器选择。例如 PA9 的 AF7 对应 USART1_TX。

**项目关联：** 本项目在 `HAL_UART_MspInit()` 中将 PA9/PA10 配置为 `GPIO_AF7_USART1`，这是复用功能配置。而 PF9 控制 LED 是普通 IO 配置，放在 `MY_GPIO_Init()` 中。**复用模式的 GPIO 配置放在 MSP 回调中，普通 IO 配置放在 drivers/gpio/ 中**，这是本项目的代码组织原则。

---

## 四、UART 串口通信

### Q8：UART 的轮询、中断、DMA 三种模式有什么区别？

**答：**

| 特性 | 轮询（Polling） | 中断（Interrupt） | DMA |
|------|-----------------|-------------------|-----|
| CPU 占用 | 100%（阻塞等待） | 低（仅中断时处理） | 几乎为零 |
| 实时性 | 差（必须等完成） | 好 | 好 |
| 编程复杂度 | 最简单 | 中等 | 较高 |
| 适用场景 | 调试打印、低频通信 | 一般通信 | 大数据量传输 |
| HAL 函数 | `HAL_UART_Transmit()` | `HAL_UART_Transmit_IT()` | `HAL_UART_Transmit_DMA()` |

**项目关联：** 本项目当前使用轮询模式 `HAL_UART_Transmit(&huart1, data, len, 1000)`，仅用于 `printf` 调试输出，满足当前需求。计划在集成 FreeRTOS 后升级为 DMA 模式，配合信号量实现非阻塞发送，避免阻塞任务调度。

---

### Q9：printf 串口重定向的原理是什么？

**答：** C 标准库的 `printf()` 最终会调用底层的 `write()` 或 `fputc()` 函数输出字符。串口重定向就是**重写这个底层函数**，将字符输出从标准输出（屏幕）重定向到 UART 串口。

实现方式有两种：
1. **重写 `fputc()`：** 适用于 Keil/IAR（微库模式），将单个字符通过 `HAL_UART_Transmit()` 发送
2. **重写 `_write()`：** 适用于 GCC/Newlib（本项目方式），将字符缓冲区通过 UART 发送

**项目关联：** 本项目使用 GCC 工具链 + Newlib，在 `retarget.c` 中重写 `_write()` 系统调用，将 `printf()` 输出重定向到 USART1。这是 `retarget_stdio_init()` 在 `main()` 中被调用的原因。

---

### Q10：UART 的波特率是怎么计算的？

**答：** STM32 的 UART 波特率由外设时钟和分频值决定：

```
波特率 = f_CK / (16 × USARTDIV)    （过采样 16 倍时）
波特率 = f_CK / (8 × USARTDIV)     （过采样 8 倍时）
```

其中 `f_CK` 是 UART 外设的输入时钟频率。USART1 挂在 APB2 总线上，USART2~5 挂在 APB1 上。

**项目关联：** 本项目 USART1 挂在 APB2（84MHz），配置波特率 115200，过采样 16 倍。USARTDIV = 84000000 / (16 × 115200) ≈ 45.57，HAL 库自动计算并写入 BRR 寄存器。

## 五、定时器（TIM）

### Q11：STM32 的定时器有哪些分类？有什么区别？

**答：** STM32F407 的定时器分三类：

| 类型 | 定时器 | 位数 | 挂载总线 | 时钟 | 特点 |
|------|--------|:----:|----------|:----:|------|
| 高级定时器 | TIM1, TIM8 | 16位 | APB2 | 168MHz | 支持互补输出、死区控制、刹车输入，用于电机控制 |
| 通用定时器 | TIM2~TIM5 | 16/32位 | APB1 | 84MHz | 支持输入捕获、输出比较、PWM、编码器接口 |
| 基本定时器 | TIM6, TIM7 | 16位 | APB1 | 84MHz | 仅支持定时中断和 DAC 触发，功能最简 |

注意：TIM2 和 TIM5 是 32 位计数器，其余通用定时器为 16 位。

**项目关联：** 本项目使用 TIM3（通用定时器，APB1，84MHz）实现 1s 周期中断翻转 LED。选择通用定时器而非基本定时器，是为后续 PWM 输出等扩展预留能力。

---

### Q12：定时器的 PSC 和 ARR 是什么？怎么计算定时周期？

**答：**
- **PSC（Prescaler）：** 预分频器，将输入时钟分频后再给计数器
- **ARR（Auto Reload Register）：** 自动重装载值，计数器从 0 数到 ARR 后溢出

计算公式：
```
中断周期 = (PSC + 1) × (ARR + 1) / TIM_CLK
```

为什么要 `+1`：硬件上分频器和计数器都是从 0 开始计数的，PSC=0 表示 1 分频（不分频），ARR=0 表示计 1 个数就溢出。

**计算举例（本项目 TIM3）：**
```
TIM_CLK = 84MHz（APB1 定时器时钟）
目标：1s

PSC = 8399  →  84MHz / (8399+1) = 10kHz，每个计数 = 0.1ms
ARR = 9999  →  (9999+1) × 0.1ms = 1000ms = 1s
```

**项目关联：** 本项目 `MY_TIM3_Init()` 中配置 `Prescaler = 8399`、`Period = 9999`，实现精确 1s 定时中断。

---

### Q13：定时器中断的完整触发链路是怎样的？

**答：** 从硬件溢出到用户回调，经过四个层次：

```
TIM3 计数器溢出（硬件自动）
  → TIM3_IRQHandler()                      ← 启动文件向量表跳转（stm32f4xx_it.c）
    → HAL_TIM_IRQHandler(&htim3)           ← HAL 库：检查中断源 + 清除标志位
      → HAL_TIM_PeriodElapsedCallback()    ← 用户回调：你的业务代码（timer.c）
```

每一层的职责：
1. **硬件层：** 计数器溢出 → 置位 UIF 标志 → 向 NVIC 发出中断请求
2. **NVIC 层：** 根据优先级决定是否响应 → 跳转到向量表中对应的 IRQHandler
3. **HAL 层：** `HAL_TIM_IRQHandler()` 判断中断类型、清除 UIF 标志、调用对应回调
4. **用户层：** `HAL_TIM_PeriodElapsedCallback()` 执行业务逻辑

**项目关联：** 本项目的回调中执行 `HAL_GPIO_TogglePin(GPIOF, GPIO_PIN_9)` 翻转 LED。回调函数是 HAL 库中 `__weak` 定义的，在 `timer.c` 中写强定义覆盖。

---

### Q14：定时器中断需要配置哪两个层面的使能？

**答：** 需要同时打开两个开关，缺一不可：

| 层面 | 函数 | 作用 |
|------|------|------|
| **外设层** | `HAL_TIM_Base_Start_IT()` | 使能 TIM 的更新中断位（TIMx->DIER 的 UIE 位），让定时器溢出时产生中断请求 |
| **NVIC 层** | `HAL_NVIC_EnableIRQ(TIM3_IRQn)` | 使能 CPU 对 TIM3 中断的响应，否则 CPU 会忽略该中断请求 |

类比理解：
- 外设层 = 门铃按钮（按下才会响）
- NVIC 层 = 门铃总开关（关掉了按也没声）

如果只调用 `HAL_TIM_Base_Start()`（不带 `_IT`），定时器会正常计数但不会触发中断。

**项目关联：** 本项目在 `HAL_TIM_Base_MspInit()` 中使能 NVIC，在 `MY_TIM3_Init()` 中调用 `HAL_TIM_Base_Start_IT()` 使能外设中断。

---

### Q15：APB1 定时器的时钟为什么是 84MHz 而不是 42MHz？

**答：** STM32F407 的时钟分配：
```
SYSCLK = 168MHz
AHB = 168MHz（1 分频）
APB1 = 42MHz（4 分频）
APB2 = 84MHz（2 分频）
```

但定时器时钟有特殊规则：**当 APB 分频系数不为 1 时，定时器时钟 = APB 时钟 × 2**。

```
APB1 分频系数 = 4（不为 1）→ TIM 时钟 = 42MHz × 2 = 84MHz
APB2 分频系数 = 2（不为 1）→ TIM 时钟 = 84MHz × 2 = 168MHz
```

这是 STM32 硬件设计决定的，目的是让定时器获得更高的时钟频率以提高定时精度。

**项目关联：** 本项目 TIM3 挂在 APB1，虽然 APB1 总线时钟是 42MHz，但 TIM3 实际输入时钟是 84MHz。PSC 和 ARR 的计算都基于 84MHz，不是 42MHz。

---

### Q16：`HAL_Delay()` 和定时器中断各自适用什么场景？

**答：**

| 特性 | `HAL_Delay()` | 定时器中断 |
|------|---------------|-----------|
| 实现方式 | 轮询 SysTick 计数器 | 硬件中断回调 |
| CPU 状态 | 阻塞等待，什么都不能做 | 空闲，可以做其他事 |
| 精度 | 1ms（受 SysTick 限制） | 可达 us 级（取决于 PSC/ARR） |
| 适用场景 | 初始化延时、简单调试 | 周期性任务、实时控制 |
| RTOS 兼容 | 会阻塞当前任务（应改用 `vTaskDelay`） | 兼容，回调中用 `FromISR` API |

**项目关联：** 本项目最初使用 `HAL_Delay(1000)` 实现 LED 闪烁，主循环被完全阻塞。改用 TIM3 定时器中断后，主循环释放为空闲，为后续集成 FreeRTOS 和添加更多任务做好准备。

## 六、HAL 库架构

### Q17：HAL 库的 MSP 回调机制是什么？（同时适用于 UART 和 TIM）

**答：** MSP（MCU Support Package）是 HAL 库的**底层硬件初始化回调机制**。HAL 库将外设初始化分为两层：

1. **协议层（HAL 库内部）：** 配置外设寄存器（波特率、数据位等） — `HAL_UART_Init()`
2. **硬件层（用户实现）：** 配置 GPIO 复用、时钟使能、DMA、NVIC — `HAL_UART_MspInit()`

HAL 库在内部定义了 `__weak`（弱定义）版本的 MSP 函数，用户在自己的代码中提供**同名强定义**版本，链接时自动覆盖。

```
调用链：HAL_UART_Init() → 内部自动调用 → HAL_UART_MspInit()（你的实现）
```

**项目关联：** 本项目在 `stm32f4xx_hal_msp.c` 中实现了 `HAL_UART_MspInit()`，完成 USART1 的 GPIO 复用配置（PA9/PA10 → AF7）和时钟使能。当调用 `HAL_UART_Init(&huart1)` 时，HAL 库自动回调此函数。

---

### Q18：`__weak` 关键字的作用是什么？

**答：** `__weak` 是 GCC/ARM 编译器的扩展属性，表示该函数是**弱符号**。链接器在链接时：

- 如果找到同名的**强符号**（普通函数定义），则使用强符号，忽略弱符号
- 如果没有找到强符号，则使用弱符号作为默认实现

HAL 库中大量使用此机制：
```c
// HAL 库中的弱定义（默认什么都不做）
__weak void HAL_UART_MspInit(UART_HandleTypeDef *huart) {
    UNUSED(huart);
}

// 用户代码中的强定义（会覆盖上面的弱定义）
void HAL_UART_MspInit(UART_HandleTypeDef *huart) {
    // 实际的 GPIO 和时钟配置
}
```

**项目关联：** 本项目的 `HAL_UART_MspInit()`、启动文件中的中断处理函数（如 `HardFault_Handler`）都利用了这一机制。启动文件中所有中断 Handler 都是 `[WEAK]` 定义，用户可以在 C 代码中覆盖。

## 七、C 语言基础（嵌入式相关）

### Q19：`extern "C"` 有什么作用？

**答：** C++ 编译器会对函数名进行**名称修饰（Name Mangling）**，在符号名中编码参数类型信息（用于支持函数重载）。而 C 编译器不会。

```c
// C 编译器生成的符号：GPIO_Init
// C++ 编译器生成的符号：_Z9GPIO_InitP17GPIO_TypeDefP15GPIO_InitTypeDef
```

`extern "C"` 告诉 C++ 编译器：**按照 C 的规则生成符号名**，不做名称修饰。这样 C 和 C++ 编译的目标文件才能正确链接。

```c
#ifdef __cplusplus
extern "C" {
#endif

void MY_GPIO_Init(void);  // 无论 C 还是 C++ 编译，符号名都是 MY_GPIO_Init

#ifdef __cplusplus
}
#endif
```

**项目关联：** 本项目所有头文件（如 `gpio.h`、`uart.h`）都加了 `extern "C"` 守护，虽然当前是纯 C 项目，但为未来可能引入 C++ 组件（如 LVGL 的 C++ 封装）预留了兼容性。

---

### Q20：`volatile` 关键字的作用？在嵌入式中为什么重要？

**答：** `volatile` 告诉编译器：**这个变量的值可能在程序控制流之外被改变**，不要对它做优化（如缓存到寄存器、删除"无用"的读写）。

嵌入式中必须使用 `volatile` 的三种场景：
1. **外设寄存器：** 寄存器值由硬件改变，编译器不知道
2. **中断共享变量：** 主循环和中断服务函数共享的全局变量
3. **多线程共享变量：** RTOS 不同任务间共享的变量

```c
// 错误：编译器可能优化掉循环中的重复读取
while (flag == 0) {}  // 编译器认为 flag 不会变，优化为死循环

// 正确：每次都从内存重新读取
volatile int flag;
while (flag == 0) {}  // 每次循环都会真正读取 flag 的值
```

**项目关联：** HAL 库中所有外设寄存器结构体的成员都声明为 `__IO`（即 `volatile`）。后续集成 FreeRTOS 后，中断回调与任务之间共享的标志变量也必须加 `volatile`。

---

### Q21：`static` 关键字在嵌入式 C 中有哪些用法？

**答：** 三种用法：

1. **修饰局部变量：** 变量存储在静态区（而非栈上），函数返回后值保留
2. **修饰全局变量：** 限制作用域为当前文件（文件作用域），其他文件不可见
3. **修饰函数：** 限制函数为当前文件私有，避免命名冲突

```c
static void SystemClock_Config(void);  // 仅 main.c 内部可见
static void Error_Handler(void);       // 仅 main.c 内部可见
```

**项目关联：** 本项目 `main.c` 中的 `SystemClock_Config()` 和 `Error_Handler()` 都声明为 `static`，因为它们只在 `main.c` 内部使用，不需要暴露给其他模块。

## 八、构建系统与工具链

### Q22：交叉编译是什么？为什么嵌入式开发需要交叉编译？

**答：** 交叉编译是指在一个平台（宿主机）上编译出另一个平台（目标机）上运行的程序。

- **宿主机：** x86/x64 架构的 PC（Windows/Linux）
- **目标机：** ARM Cortex-M4 架构的 STM32

嵌入式设备通常资源有限（内存小、无操作系统），无法在目标机上直接运行编译器，所以需要在 PC 上用交叉编译器生成 ARM 指令集的机器码。

**项目关联：** 本项目使用 `arm-none-eabi-gcc` 交叉编译工具链，通过 CMake + Ninja 构建。`arm-none-eabi` 表示：arm 架构、无操作系统厂商（none）、无特定 ABI 约束（eabi）。

---

### Q23：ELF、BIN、HEX 文件有什么区别？

**答：**

| 格式 | 内容 | 用途 |
|------|------|------|
| ELF | 包含代码 + 调试信息 + 符号表 + 段信息 | GDB 调试、符号分析 |
| BIN | 纯二进制机器码，按内存地址排列 | OpenOCD/ST-Link 直接烧录 |
| HEX | Intel HEX 格式，包含地址信息的文本文件 | ISP 串口下载、部分烧录工具 |

从 ELF 生成 BIN/HEX：
```bash
arm-none-eabi-objcopy -O binary firmware.elf firmware.bin
arm-none-eabi-objcopy -O ihex firmware.elf firmware.hex
```

**项目关联：** 本项目 CMake 构建生成 `.elf` 文件用于 OpenOCD + DAP-Link 调试下载。

## 九、通信协议（项目规划相关）

### Q24：MQTT 协议的工作原理？QoS 等级有什么区别？

**答：** MQTT 是基于发布/订阅模式的轻量级物联网协议，由三个角色组成：
- **Publisher（发布者）：** 发送消息到某个 Topic
- **Subscriber（订阅者）：** 订阅感兴趣的 Topic
- **Broker（代理服务器）：** 接收发布者的消息，转发给订阅者

QoS（服务质量）等级：

| QoS | 名称 | 保证 | 适用场景 |
|-----|------|------|----------|
| 0 | At most once | 最多一次，可能丢失 | 传感器周期上报（丢一次无所谓） |
| 1 | At least once | 至少一次，可能重复 | 控制指令（重复执行可接受） |
| 2 | Exactly once | 恰好一次，不丢不重 | 计费、关键状态变更 |

**项目关联：** 本项目规划通过 ESP8266（AT 指令模式）连接 MQTT Broker，将传感器数据上报到云端。传感器数据使用 QoS 0 即可，控制指令下发建议使用 QoS 1。

---

### Q25：Modbus RTU 协议的帧结构是怎样的？

**答：** Modbus RTU 是工业领域最常用的串口通信协议，采用主从架构，二进制编码。

帧结构：
```
| 从机地址(1B) | 功能码(1B) | 数据(NB) | CRC校验(2B) |
```

常用功能码：
- `0x01`：读线圈（DO）
- `0x03`：读保持寄存器（AO）
- `0x05`：写单个线圈
- `0x06`：写单个寄存器
- `0x10`：写多个寄存器

帧间隔通过 3.5 个字符的静默时间判断（与波特率相关）。

**项目关联：** 本项目规划支持 Modbus RTU 协议用于工业设备通信，STM32 作为 Modbus 主站，通过 RS485 接口（UART + DE/RE 引脚控制收发方向）读取从站设备数据。

## 十、RTOS 基础（项目规划相关）

### Q26：为什么需要 RTOS？裸机开发有什么问题？

**答：** 裸机开发通常采用**超级循环（Super Loop）**架构：

```c
while (1) {
    task1();  // 如果这里阻塞 1s（如 HAL_Delay）
    task2();  // 这里就要等 1s 才能执行
    task3();
}
```

问题：
1. **实时性差：** 一个任务阻塞会影响所有任务的响应时间
2. **时序耦合：** 任务之间的执行顺序和时间紧密耦合
3. **扩展性差：** 新增任务可能打破现有的时序平衡

RTOS 通过**抢占式调度**解决这些问题，每个任务独立运行，高优先级任务可以抢占低优先级任务。

**项目关联：** 本项目当前就是超级循环架构（`while(1)` 中 LED 翻转 + printf + HAL_Delay）。后续需要同时处理传感器采集、MQTT 上报、Modbus 通信、LVGL 界面刷新等多个任务，必须引入 FreeRTOS 进行任务管理。

---

### Q27：FreeRTOS 的任务状态有哪些？

**答：** FreeRTOS 任务有四种状态：

```
           ┌─────────┐
    创建 → │ Ready   │ ←── 事件/超时
           └────┬────┘
                │ 调度器选中
                ▼
           ┌─────────┐
           │ Running  │ ──── 只有一个任务处于此状态
           └────┬────┘
           ┌────┴────┐
    等待事件│         │ 延时/挂起
           ▼         ▼
      ┌─────────┐ ┌──────────┐
      │ Blocked │ │ Suspended│
      └─────────┘ └──────────┘
```

- **Running：** 正在 CPU 上执行（同一时刻只有一个）
- **Ready：** 就绪，等待调度器分配 CPU
- **Blocked：** 等待某个事件（延时、信号量、队列），有超时限制
- **Suspended：** 被主动挂起（`vTaskSuspend`），只能被 `vTaskResume` 唤醒

**项目关联：** 后续项目中，传感器采集任务可能因等待 I2C 数据而进入 Blocked 状态，此时 CPU 可以去执行 LVGL 刷屏任务，实现多任务并发。

---

### Q28：FreeRTOS 中任务间通信有哪些方式？

**答：**

| 机制 | 用途 | 典型场景 |
|------|------|----------|
| 队列（Queue） | 任务间传递数据 | 传感器数据从采集任务传给上报任务 |
| 信号量（Semaphore） | 同步/互斥 | DMA 传输完成通知、串口资源互斥 |
| 互斥量（Mutex） | 资源保护（带优先级继承） | 多任务共享 SPI 总线 |
| 事件组（Event Group） | 多事件等待/同步 | 等待"网络就绪 AND 传感器就绪" |
| 任务通知（Task Notification） | 轻量级信号量/邮箱 | 中断通知任务处理数据 |

**项目关联：** 本项目集成 FreeRTOS 后，计划使用队列传递传感器数据，使用信号量同步 DMA 传输完成，使用互斥量保护共享 SPI 总线（W25Q128 Flash 和 TF 卡共用）。

## 十一、项目整体架构

### Q29：你的项目分层架构是怎么设计的？为什么要分层？

**答：** 本项目采用六层分层架构：

```
APP（应用层） → Services（服务层） → Drivers（驱动层） → BSP（板级支持） → Platform（平台层） → External（外部库）
```

**分层的意义：**
1. **解耦：** 上层不直接依赖硬件，更换硬件平台只需修改底层
2. **可测试：** 可以 Mock 底层接口，单独测试业务逻辑
3. **可维护：** 每层职责清晰，修改影响范围可控
4. **可复用：** 驱动层和服务层可以复用到其他项目

**具体划分原则：**
- APP：main 函数、任务创建、业务流程
- Services：MQTT 客户端、Modbus 协议栈、数据处理
- Drivers：GPIO、UART、SPI、I2C 等外设驱动
- BSP：板级硬件差异（LED 引脚、按键引脚等）
- Platform：启动文件、链接脚本、系统时钟配置
- External：HAL 库、FreeRTOS、LVGL 等第三方库

---

### Q30：AT 指令模式和 LwIP 原生模式有什么区别？你为什么选择先用 AT 模式？

**答：**

| 对比项 | AT 指令模式 | LwIP 原生模式 |
|--------|-------------|---------------|
| 架构 | STM32 → UART → ESP8266 → Wi-Fi | STM32(LwIP) → RMII → LAN8720 → 以太网 |
| TCP/IP 栈 | 运行在 ESP8266 上 | 运行在 STM32 上 |
| 吞吐量 | ~11KB/s（受 UART 限制） | 10/100Mbps |
| 开发难度 | 低（AT 字符串命令） | 高（需理解协议栈、网络编程） |
| 硬件成本 | ESP8266 模组 ~5 元 | LAN8720 PHY ~3 元 + 网口 |
| 可扩展性 | 弱（受限于 AT 指令集） | 强（可实现 HTTP Server、WebSocket） |

**选择策略：** 先用 AT 模式快速实现功能闭环（传感器 → MQTT → 云端），验证业务逻辑。后续再升级为 LwIP 模式，增加嵌入式 Web 服务器、本地直连等高级功能，提升项目的技术深度和简历竞争力。
